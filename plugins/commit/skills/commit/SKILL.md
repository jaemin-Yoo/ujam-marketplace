## 커밋 절차

### 0단계: 브랜치 확인

위 "현재 브랜치"와 "로컬 브랜치 목록"을 기준으로 아래 규칙에 따라 판단합니다.

**현재 브랜치가 `main`인 경우:**

1. **로컬 브랜치가 `main` 하나뿐인 경우**: 확인 질문 없이 바로 다음 단계로 진행합니다.
2. **`main` 외에 다른 로컬 브랜치가 존재하는 경우**: 커밋을 진행하기 전에 **반드시 사용자에게 확인**합니다. 이때 존재하는 다른 브랜치 이름을 함께 알려줍니다. (예: "현재 `main` 브랜치이며, 다른 브랜치(`feature/login`, `fix/typo`)가 존재합니다. 이대로 `main`에 커밋할까요?") 사용자가 명시적으로 동의한 경우에만 다음 단계로 진행하고, 다른 브랜치를 원하면 브랜치를 전환한 뒤 진행합니다.
   - 단, 스킬 호출 시 인자(args)에 `main`이 포함된 경우(예: `/commit main`)에는 사용자가 이미 main 브랜치 커밋을 명시적으로 승인한 것으로 간주하고, 확인 질문 없이 바로 다음 단계로 진행합니다.

**현재 브랜치가 `master`인 경우:** 브랜치 개수나 인자와 무관하게 항상 커밋 전에 사용자에게 확인합니다.

**그 외 브랜치인 경우:** 확인 없이 바로 다음 단계로 진행합니다.

### 1단계: 작업 범위 판단

**현재 대화에서 수행한 작업이 있는 경우** (Claude가 파일을 생성·수정·삭제한 경우):
- 해당 파일들을 스테이징하고 커밋합니다.
- 커밋 메시지는 대화에서 수행한 작업 내용을 기반으로 작성합니다.

**현재 대화에서 수행한 작업이 없는 경우**:
- `git status`와 `git diff`로 확인된 전체 변경 사항을 기준으로 커밋합니다.

### 2단계: 작업 분리 판단

변경 사항이 아래 조건에 해당하면 **반드시 분리하여 커밋**합니다:

- 서로 다른 기능(feature) 변경이 혼재
- 버그 수정(fix)과 기능 추가가 혼재
- 리팩토링과 신규 기능이 혼재
- 독립적인 모듈/컴포넌트에 영향을 미치는 변경이 혼재

각 논리적 단위를 별도 커밋으로 나누어 순서대로 진행합니다.

### 3단계: 커밋 메시지 작성

**Conventional Commit 형식을 따릅니다:**

```
<타입>: <설명>

[본문 - 선택]

[푸터 - 선택]
```

**타입:**

| 타입 | 용도 |
|------|------|
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 변경 |
| `style` | 코드 스타일 변경 (기능 무관) |
| `refactor` | 리팩토링 |
| `test` | 테스트 추가/수정 |
| `chore` | 유지보수 작업 |

**예시:**
```
feat: 비밀번호 재설정 기능 추가

- 비밀번호 찾기 폼 추가
- 이메일 인증 플로우 구현
- 비밀번호 재설정 엔드포인트 추가
```

### 주의사항

- 커밋 전 변경 사항을 반드시 검토합니다.
- 민감한 정보(`.env`, 자격증명 파일 등)가 포함되지 않도록 확인합니다.
- 관련 파일이 스테이징되지 않았으면 함께 스테이징합니다.
- `git add -A` 대신 파일을 명시적으로 지정하여 스테이징합니다.
- 커밋 메시지에 `Co-Authored-By` 트레일러를 추가하지 않습니다.
